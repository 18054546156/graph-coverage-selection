1. 三条流程分别是什么

当前项目里存在两条不同用途的 Table 1 路径。它们不能混写成一个实验。

作者公开 runtime

读取 train读取 MedMNIST train，生成或读取 UNI embedding / dynamics。
选择子集按比例和方法选择，每个类别有预算。
训练 ResNet-18在选中子集上训练；默认 runtime 支持 epoch 或 iteration 两种范式。
周期性 test作者代码每 10 个 epoch 或固定 iteration 间隔评估 test，并记录 best test BA 和 final BA。

证据：original_author/graphcov/run/experiment.py:150-177, 391-454, 560-822；original_author/graphcov/run/evaluation.py:348-552。

当前项目的 strict Table 1 runner

Job 1：只选择只读取 train，生成冻结的 selected indices 和 hash。
Job 2：只训练读取冻结索引，在 selected train 上训练。
validation 选 checkpoint每 10 epoch 在 validation 上算 BA，只保存 validation BA 最好的 checkpoint。
test 一次训练结束后加载 best validation checkpoint，只在 test 上评估一次。

证据：table1_reproduction/experiments/job1_select.py:170-380；table1_reproduction/experiments/job2_downstream.py:170-235、:285-330；configs/job2_table1.json。

这条 strict 流程的优点：test 不参与 checkpoint 选择，避免用 test 反复挑最好 epoch。它是当前项目的防泄漏复现协议，但不是作者公开 runtime 原样行为。

当前项目的 clean-only paired-seed runner

读取 clean train不读取 MedMNIST-C，不使用 corrupted train。
选择 clean 子集使用一个 SELECTION_SEED，按 2% 或 5% 和 8 个方法选择。
clean selected training用对应 TRAINING_SEED 训练 1000 epochs。
clean test final不做 validation checkpoint 选择，训练结束后用 final epoch 模型测 clean test。

证据：table1_clean_only_20260922/run_clean_only.slurm:43-85、:95-126；pipeline.clean_only.patch.py:572-610、:869-930、:1069-1165、:1325-1350。

因此 clean-only 不是 strict runner 的同义词：它是为估计 paired seed 下结果波动而建立的独立实验。它能回答“选样随机性和训练随机性一起变化时结果如何”，不能直接称为作者 runtime 的逐字复现。

2. 方法本身：当前项目和作者是否一样

方法作者实现当前项目实际使用判断
Random按类别随机选样，seed 控制随机抽样。strict 使用官方选择接口；clean-only 在 choose() 中用当前 selection seed。核心相同，seed 口径不同。
EL2N读取早期训练 dynamics 的错误分数，按分数选样。28×28 dynamics、200 epochs，并调用同一方法注册表。核心相同，缓存/编排不同。
Forgetting按正确到错误的 forgetting 事件计数。复用同一 dynamics 产生方式和选择接口。核心相同。
EVA从 dynamics 的早晚窗口计算误差变化/波动。使用同一 28×28、200 epoch、window=10 约定。核心相同，需保证窗口和 seed 一致。
Facility按 cosine 相似度做 greedy facility location；公开实现可构建 dense 矩阵。strict/clean-only 使用 blockwise cosine 计算，避免 TissueMNIST dense 矩阵爆内存。目标函数相同，浮点累积、tie-breaking 和内存路径可能不同。
FPS按 farthest-point 递推，每类选样，第一点受 seed 影响。调用作者选择函数；clean-only 每个 paired seed 都重新选择。核心相同，seed 传播不同。

Graph-A2 的关键风险：不能只看到方法名相同就认为实验相同。作者 CLI 默认是 k=10 且 global 不是默认值；当前 strict/clean-only 为了对齐 Table 1 证据显式使用 k=50、H=2、global。若原论文 Table 1 实际采用的配置没有被补充材料明确写出，这里仍然存在可审计的实现假设。

4. 随机种子：作者、strict 和 clean-only 的真正区别

作者公开 runtime 的 seed 传播

作者在 experiment.py 中用 seed = config['seed'] + trial，CLI 默认 base seed 是 42。因此 5 个 trial 通常对应训练 seed：

trial 0 → 42
trial 1 → 43
trial 2 → 44
trial 3 → 45
trial 4 → 46

作者对选择结果做了缓存：random、FPS 等非确定性方法不缓存，会随 trial seed 变化；Graph-A2、Facility、Herding、EL2N、Forgetting、EVA 等确定性方法缓存第一次选择结果，通常固定为第一 trial 的 selection seed 42。作者代码证据见 experiment.py:391-454 和 :656-720。

当前 strict runner 的 seed 策略

方法类别selection seedtraining seed是否与作者策略接近
Random、FPS42、43、44、45、46，跟每个 trial 的 training seed 走。42、43、44、45、46。接近作者公开 runtime。
其余确定性方法固定 42，只生成一个 frozen subset。42、43、44、45、46。接近作者缓存逻辑。

代码证据：table1_reproduction/experiments/job1_select.py:170-176；configs/job1_table1.json 的 selection_seed_policy。

当前 clean-only paired seed 的 seed 策略

seed 42: selection_seed=42, training_seed=42
seed 43: selection_seed=43, training_seed=43
seed 44: selection_seed=44, training_seed=44

clean-only 的 choose() 对所有 8 个方法都传入同一个 SELECTION_SEED；之后 run_one() 再传入对应的 train_seed。所以在 clean-only 中，即使是 Graph-A2、Facility、Herding 等“确定性方法”，seed 42 和 seed 43 也会生成不同选集，随后训练也使用不同 seed。

这意味着：clean-only 的 42→43 差异是“选集变化 + 训练变化”的联合差异，不是纯 training-seed 方差。若要估计纯训练随机性，应冻结 selection index/hash，只改变 training seed；若要估计真实端到端复现波动，当前 paired 设计是合理的，但必须这样解释。

5. 当前项目是否已经“完全按作者流程”

问题结论解释
选择方法代码是否完全换成了新方法？没有strict Table 1 使用固定作者源码副本；clean-only 复用作者方法接口并加入自己的编排/审计逻辑。
数据集、比例、类别均衡是否相同？大体相同五个 MedMNIST 数据集、2%/5%、按类别预算；有效预算是 floor(floor(n×ratio)/n_classes)。
Graph-A2 的参数是否自动等于作者默认值？不是当前显式使用 k=50/global/H=2；作者 CLI 默认 k=10、global 关闭。
训练是否逐行相同？不是当前项目有 strict validation runner 和 clean-only final runner；作者公开 runtime 的 checkpoint/test 逻辑不同。
seed 是否相同？取决于 pipelinestrict 接近作者：确定性方法固定 selection=42；clean-only 明确采用 selection=train 的 paired seed。
test 是否参与模型选择？strict 不参与，作者 raw 会参与，clean-only 不参与作者 raw 周期性 test 并记录 best test；strict 用 val；clean-only 只在 final epoch 测 clean test。
能否把 clean-only 数值直接叫“作者 Table 1 严格复现”？不能它是 clean-only paired-seed 扩展，适合研究 seed 敏感性，不是原作者 runtime 的逐字复刻。

6. 为什么差距可能很大

  1. 训练长度口径：作者 README 示例的 1000 iterations 与当前 1000 epochs 不是同一个计算量；每个 epoch 会遍历整个 selected train。
  2. checkpoint 口径：best test、best validation 和 final epoch 是三个不同指标来源。即使模型完全相同，最终 BA 也可能不同。
  3. Graph-A2 配置：k=10 与 k=50、global 与 per-class 会改变图覆盖关系和选集。
  4. Facility 数值路径：blockwise 实现目标等价，但浮点累积和候选 tie 的细节可能改变极少数边界选择。
  5. seed 联动：clean-only 同时改变 selection 和 training；不能把它与 strict 的“固定选集、多 training seed”结果混合。
  6. GPU 确定性：clean-only 开启 deterministic，作者默认关闭；这改变运行速度，也可能改变 CUDA 算子结果。
因此目前最严谨的表述：结果显示项目当前实现与论文报告存在差异，但尚未证明差异来自某一个算法 bug。必须先统一训练范式、checkpoint 规则、Graph-A2 参数和 seed policy，才能把剩余差距归因到代码或硬件。
